# Архитектура

## Задача

Ежемесячная передача показаний счётчиков воды и электричества. У поставщика нет API,
показания вводятся руками на сайте. Цель — свести участие человека к минимуму и
не давать забыть о сроке.

## Две части и одна связь между ними

```
┌──────────────────────────┐          ┌─────────────────────────────┐
│  Android (MAUI)          │          │  Обработчик (Windows, .NET) │
│                          │          │                             │
│  съёмка фото             │          │  наблюдение за папкой       │
│  локальные уведомления   │          │  распознавание (VLM на GPU) │
│  экран подтверждения     │          │  прогноз при отсутствии фото│
│  настройки обеих частей  │          │  ввод в кабинет (Playwright)│
│  offline-очередь         │          │  письмо с результатом       │
└───────────┬──────────────┘          └──────────────┬──────────────┘
            │                                        │
            └──────────────► Dropbox App Folder ◄─────┘
                    /config  /photos  /queue  /state
```

Между частями нет ни своего сервера, ни push-сервиса, ни открытых портов. Всё
взаимодействие — файлы в папке приложения Dropbox. Это осознанный выбор: система
для одной семьи не должна требовать хостинга, домена и сертификата, а Dropbox уже
решает синхронизацию, авторизацию и доступность.

## Dropbox как очередь, а не как хранилище

Ключевая идея: папка используется как **очередь сообщений с состоянием**, а не просто
как место для файлов.

```
pending ──(атомарный Move)──► processing ──► done
                                   │
                                   └────────► failed
```

Почему именно так:

* **Захват задачи атомарным `MoveV2`.** Если обработчиков окажется два (запустили
  вторую копию, перезапустили не дождавшись), задачу получит ровно один: второй
  получит конфликт. Без этого показания можно отправить дважды.
* **Файл, застрявший в `processing`, — это точный список того, что нужно
  переобработать** после падения процесса. Не нужен отдельный журнал.
* **`autorename=false` обязателен.** По умолчанию Dropbox при конфликте молча создаёт
  «file (2).json». Это тихо ломает и захват задачи, и дедупликацию: ошибки нет,
  поведение неверное. Флаг выключен явно, и на это есть тесты.

## Идемпотентность

Обработчик обязан быть идемпотентным на каждом шаге: задача может упасть между
распознаванием и отправкой, между отправкой и записью истории.

Механизмы:

* `MessageId` — ключ идемпотентности. Для задач, которые обе стороны могут породить
  независимо (прогноз за период), идентификатор детерминированный:
  `submitforecast-2026-07`. Дубль схлопывается, даже если первая задача уже уехала
  в `processing` или `done`.
* Перед вводом в кабинет проверяется признак «период уже закрыт». Это дешевле и
  надёжнее, чем полагаться только на собственную запись об отправке.

## Слои

| Проект | Содержимое | Зависимости |
|---|---|---|
| `WaterCounters.Core` | контракты, очередь, Dropbox, настройки, крипто, прогноз, валидация | Dropbox.Api |
| `WaterCounters.Portal` | ввод показаний в кабинет | Core, Playwright |
| `WaterCounters.Recognition` | распознавание фото | Core, HTTP-клиент VLM, OpenCV |
| `WaterCounters.Desktop` | хост: наблюдатель, обработчик, watchdog, почта | Core, Portal, Recognition |
| `WaterCounters.Mobile` | тонкий UI поверх Core | Core |

Логика, которую используют **обе** части, живёт в Core. Пример: расчёт срока сдачи
и льготного периода. Телефон по нему шлёт напоминания, обработчик по нему же решает,
пора ли считать прогноз. Две реализации разошлись бы, и расхождение проявилось бы
раз в месяц в худший момент.

## Что где проверяется

* Логика (очередь, прогноз, валидация, крипто) — модульными тестами на
  `InMemoryRemoteStore`, без сети.
* Транспорт Dropbox — командой `smoke` утилиты `WaterCounters.DropboxSetup`
  на живом аккаунте: конфликты, атомарность, longpoll.
* Ввод в кабинет — настоящим Chromium против макета кабинета с серверной сессией.
* Распознавание — прогоном по размеченным фикстурам с подсчётом доли точных
  совпадений; модель выбирается замерами, а не на глаз.
