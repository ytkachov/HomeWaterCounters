# Протокол обмена через Dropbox

Тип приложения в консоли Dropbox — **Scoped access → App folder**: приложение видит
только собственную папку. Все пути ниже — относительно неё.

## Раскладка папок

```
/config/settings.json          несекретные настройки, редактируются с телефона
/config/secrets.enc            AES-256-GCM: доступ к кабинету, пароль SMTP
/state/history.json            история сданных показаний
/photos/2026-07/cold-water.jpg фотографии периода
/queue/to-desktop/<id>.json    сообщения обработчику
/queue/to-mobile/<id>.json     сообщения телефону
/queue/processing/<id>.json    задача захвачена обработчиком
/queue/done/2026-07/<id>.json  архив выполненных
/queue/failed/<id>.json        + <id>.json.error.txt с причиной
```

## Конверт сообщения

```json
{
  "schemaVersion": 1,
  "messageId": "1767225600000-a3f1c2b8",
  "type": "SubmitReadings",
  "period": "2026-07",
  "deviceId": "pixel-8",
  "createdUtc": "2026-07-05T10:15:00+00:00",
  "payload": { }
}
```

`messageId` — 13 цифр Unix-времени в миллисекундах и 8 случайных hex. Лексикографическая
сортировка совпадает с хронологической, поэтому список файлов в папке уже отсортирован
по времени. Для задач, порождаемых обеими сторонами независимо, идентификатор
детерминированный: `submitforecast-2026-07`.

`payload` намеренно нетипизирован в конверте: получатель со старой схемой прочитает
конверт, увидит незнакомый `type` и отложит сообщение, а не упадёт на десериализации.

## Типы сообщений

| Направление | Тип | Payload |
|---|---|---|
| телефон → обработчик | `SubmitReadings` | `[{meterKey, photoPath, capturedUtc}]` |
| телефон → обработчик | `SubmitForecast` | `{reason}` — фотографий не будет |
| телефон → обработчик | `ReadingsConfirmed` | `{proposalId, readings:[{meterKey, value, wasEdited}]}` |
| телефон → обработчик | `ReadingsRejected` | `{proposalId, reason}` |
| обработчик → телефон | `ReadingsProposed` | `{proposalId, sourceMessageId, isForecast, readings:[…]}` |
| обработчик → телефон | `ForecastUnavailable` | `{reason, meterKeys}` |
| обработчик → телефон | `SubmissionSucceeded` | `{readings, receiptScreenshotPath, wasDryRun}` |
| обработчик → телефон | `SubmissionFailed` | `{error, screenshotPath, tracePath, attemptCount}` |
| обработчик → телефон | `DesktopStatus` | `{version, lastSeenUtc, vlmModel, health}` |

## Порядок при отправке фотографий

Отправитель сначала загружает **все** файлы, и только потом кладёт сообщение в очередь.
Файл сообщения — commit-маркер комплекта: обработчик никогда не увидит наполовину
загруженный набор.

Это правило действует и при ручной раскладке фотографий — см.
[recognition-service.md](recognition-service.md), раздел про определение готовности пачки.

## Жизненный цикл задачи

1. `ListPendingAsync` — что лежит в папке направления.
2. `TryClaimAsync` — атомарный `Move` в `processing`. Результат:
   * `Claimed` — задача наша, конверт разобран;
   * `TakenByOther` — забрал другой обработчик либо файл уже уехал; это не ошибка;
   * `Poisoned` — файл не разбирается, уже перемещён в `failed` рядом с текстом ошибки.
     Битое сообщение не должно вечно всплывать в очереди и мешать остальным.
3. Обработка.
4. `CompleteAsync` — в архив периода, либо `FailAsync` — в `failed` с причиной.

При старте вызывается `RecoverAbandonedAsync`: всё, что осталось в `processing`, —
это задачи, прерванные падением процесса.

## Наблюдение за изменениями

`GetCursorAsync` даёт отправную точку, `WaitForChangesAsync` — longpoll до 480 секунд.
Соединение висит подолгу намеренно: это дешевле опроса и не расходует батарею.
При ошибке longpoll обработчик деградирует до периодического опроса.

## Настройки и секреты

`settings.json` содержит только несекретное: список счётчиков, срок сдачи, льготный
период, карту селекторов кабинета, адрес получателя писем, параметры распознавания.
Поля `revision`, `updatedUtc`, `updatedBy`; сторона с меньшей ревизией не перезаписывает
большую.

`secrets.enc` — AES-256-GCM, ключ из PBKDF2-SHA256 (600 000 итераций) от мастер-пароля,
который вводится один раз на каждом устройстве. Заголовок входит в associated data,
поэтому подмена числа итераций ломает проверку тега так же, как подмена шифротекста.
Dropbox не видит открытых секретов.
