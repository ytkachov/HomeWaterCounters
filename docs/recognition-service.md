# Обработчик фотографий: спецификация

Часть, работающая на машине с GPU. Забирает фотографии из Dropbox, распознаёт
показания локальной VLM-моделью, проверяет их и вводит в личный кабинет.

Состояние: реализовано и покрыто тестами всё, кроме подбора модели — он требует
машины с GPU и реальных фотографий. `WaterCounters.Recognition` проверяется на
заглушечном HTTP-сервере, `WaterCounters.Desktop` — на `InMemoryRemoteStore`,
`StubRecognizer` и макете кабинета.

## Режим первого этапа: фотографии раскладываются вручную

Мобильного приложения пока нет. Фотографии кладутся в Dropbox руками, поэтому
сообщения `SubmitReadings` никто не отправляет — обработчик должен сам заметить
появление фотографий.

Это отличается от целевой схемы ровно одним: источником события. Всё, что дальше
распознавания, одинаково и переиспользуется, когда появится телефон.

### Определение готовности пачки

Ручная загрузка приходит файл за файлом в течение секунд или минут. Обрабатывать
после первого же файла нельзя — уйдут неполные показания.

Правило:

* пачка готова, если для каждого настроенного счётчика есть фотография — это
  нормальный случай, реакция почти мгновенная;
* иначе — если в папке периода не появлялось новых файлов `settlingMinutes`
  минут (по умолчанию 3) и есть хотя бы одна фотография. Это случай «сняли не все
  счётчики» или «один файл не долетел»; такая пачка обрабатывается, а недостающие
  счётчики попадают в письмо как требующие внимания.

Повторная обработка периода не запускается: признак — запись в `state/history.json`
либо закрытый период в кабинете.

### Сопоставление фотографии со счётчиком

По порядку, до первого совпадения:

1. Имя файла совпадает с ключом счётчика из настроек: `cold-water.jpg`,
   `hot-water.jpg`, `electricity.jpg`. Основной способ при ручной раскладке —
   явный, предсказуемый, не зависит от качества снимка.
2. Серийный номер, распознанный на фото, совпадает с настроенным у счётчика.
   Спасает, когда файлы называются `IMG_1234.jpg`.
3. Не удалось — фотография помечается как нераспознанная, показание по этому
   счётчику не отправляется, факт попадает в письмо.

Когда сработал способ 1, серийный номер всё равно сверяется: несовпадение почти
всегда означает, что счётчики сняты не в том порядке. Это опаснее неверной цифры —
неправильными окажутся оба показания.

### Подтверждение перед отправкой

Целевая схема — подтверждение на телефоне. Пока телефона нет, роль подтверждения
играет режим проверки: `portal.dryRun = true` в настройках (значение по умолчанию).

В этом режиме обработчик делает всё, кроме нажатия кнопки отправки: заполняет форму,
снимает скриншот и шлёт письмо с распознанными значениями, потреблением за период и
скриншотом заполненной формы. Убедившись на одном-двух месяцах, что цифры верны,
переключаете `dryRun` в `false`.

Отправка показаний необратима, поэтому по умолчанию она выключена намеренно.

## Контракт распознавания

```csharp
public interface IMeterRecognizer
{
    Task<RecognitionResult> RecognizeAsync(
        MeterSpec meter, ReadOnlyMemory<byte> jpeg, CancellationToken ct);
}

public sealed record RecognitionResult(
    string? Serial,
    decimal? Value,
    double Confidence,
    string RawJson,
    IReadOnlyList<string> Warnings);
```

Реализации:

| Класс | Назначение |
|---|---|
| `OllamaRecognizer` | основной: POST /api/chat, картинка в images[], схема в format |
| `OpenAiCompatibleRecognizer` | LM Studio, llama.cpp, vLLM: /v1/chat/completions |
| `EnsembleRecognizer` | 2–3 прохода с разными кропами, голосование большинством |
| `StubRecognizer` | ожидаемое значение из имени файла фикстуры; для разработки без GPU |

Endpoint и имя модели — из настроек. VLM-хост может стоять и на другой машине в
локальной сети: меняется только URL.

### Схема ответа

Ollama с версии 0.5 принимает в поле format полноценную JSON Schema, а не только
строку json. Модель физически не может вернуть текст не по схеме — это надёжнее
любого разбора свободного текста регулярками.

```json
{
  "type": "object",
  "properties": {
    "serial":            { "type": ["string", "null"] },
    "integer_part":      { "type": "string" },
    "fractional_part":   { "type": ["string", "null"] },
    "value":             { "type": "number" },
    "digit_confidences": { "type": "array", "items": { "type": "number" } },
    "confidence":        { "type": "number" },
    "notes":             { "type": "string" }
  },
  "required": ["integer_part", "value", "confidence"],
  "additionalProperties": false
}
```

Параметры запроса: temperature 0, stream false.

### Что должен содержать промпт

* сколько разрядов до и после запятой ожидается — берётся из `MeterSpec`;
* что на водосчётчиках красные разряды это дробная часть;
* что при перекате барабана берётся меньшая цифра и ставится пометка;
* что серийный номер возвращается ровно как напечатан, без домысливания.

### Предобработка (OpenCvSharp4)

Коррекция ориентации по EXIF, поиск контура лицевой панели и перспективное
выравнивание, затем два варианта на вход модели: полный кадр и тесный кроп
циферблата. `Mat` — только через using-декларации.

**CLAHE выключен по умолчанию.** Замер на реальных снимках показал устойчивое
ухудшение — 80 % по целой части без него против 60 % с ним. Счётчики почти всегда
сняты в тёмной нише, то есть выравнивание срабатывало на каждом кадре и вытягивало
вместе с цифрами шум и блики на стекле. Включается флагом `enhanceDarkFrames` в
настройках — но только если замер на ваших снимках скажет обратное.

**Поиск панели на водосчётчиках не работает** и это известное ограничение:
`TryFindPanel` ищет выпуклый четырёхугольник, а лицевая панель у них круглая, так
что код всегда уходит в запасной центральный кроп. Порог берётся и без него,
поэтому чинить не стали.

### Выбор модели

Не на глаз, а замерами. `tools/WaterCounters.Recognition.Bench`: на вход папка
`fixtures/meters/<meterKey>_<ожидаемое>_<серийник>.jpg`, на выход по каждой комбинации
модель × промпт × препроцессинг × кадры — доля точных совпадений, доля ошибочных
цифр, средняя задержка.

Ключ `--dump` складывает кадры ровно в том виде, в каком они уходят модели. Без него
разбор «почему не читается» превращается в гадание: метрика говорит, что модель
ошиблась, но не говорит, что она видела. Ключи `--images` и `--enhance` разводят
кроп и выравнивание яркости по отдельным измерениям — иначе их вклад не разделить.

Размер контекста задаётся явно (`contextTokens`, по умолчанию 8192). Умолчание
Ollama — 4096 токенов, и полноразмерный кадр в него не помещается: хост отвечает
`400 exceeds the available context size` ещё до того, как модель что-то увидит.

Что дал первый прогон по реальным снимкам, помимо выбора модели:

| Находка | Разница |
|---|---|
| `num_ctx` не задавался — Ollama отказывала на полном кадре | не работало вовсе → работает |
| CLAHE на тёмных кадрах вытягивает шум до уровня цифр | 60 % → 80 % |
| Ужатие кадра до 1280 px — барабан занимает малую долю | 40 % → 100 % |
| Короткий промпт вместо подробного | 80 % → 100 %, вчетверо меньше неверных цифр |
| Q8 вместо Q4 | 20 % → 40 % |
| Серийный номер отдельным запросом | 20 % → 80 % точных, неверных цифр 18 % → 2.6 % |

Последняя строка — самая крупная находка после выбора модели. Просьба заодно
прочитать серийный номер отнимает у модели внимание от цифр, а сам номер при этом
обязателен: по нему хост понимает, какой счётчик на снимке, когда в квартире два
холодных и два горячих. Два коротких запроса — один про показание, другой про номер —
дают и то и другое: `separateSerialPass` включён по умолчанию. Платой служит время,
вдвое больше на снимок.

Отдельно проверено и **отвергнуто**: вариант «модель отдаёт показание одной строкой,
делим сами». Раскладку по разрядам модели делают неверно, но одна строка эту болезнь
не лечит — разделитель всё равно ставится не туда, а доля неверных цифр вчетверо выше.
Раздельные поля дают модели больше структуры.

### Устойчивость к условиям съёмки

Ключ `--augment N` портит каждую фикстуру предсказуемым образом: темнее, светлее,
поворот ±12°, наклон, смаз, шум, блик. Это **мера устойчивости, а не способ увеличить
выборку** — варианты одного кадра не независимы, и отчёт печатает это первой строкой,
чтобы доля совпадений не выглядела весомее, чем есть.

Прогон по пяти снимкам в девяти вариантах каждый (45 наблюдений): целая часть 97.8 %,
серийные номера 95.6 %. Семь искажений из восьми не стоили ни одной ошибки по целой
части; единственный промах дал поворот по часовой стрелке на электросчётчике.

Оставшиеся расхождения — последний красный разряд на двух снимках горячей воды,
смазанный съёмкой с рук в темноте. Модель уверена в нём на 98 %, то есть порог
`minConfidence` такую ошибку не удержит. На отправку это не влияет: кабинет принимает
целые кубометры, и `valueDecimals` отбрасывает дробную часть до передачи. Лечится не
моделью, а упором для телефона при съёмке.

Прогоны детерминированы **в пределах одной машины**: три одинаковых замера дают
побайтово одинаковый результат. Между машинами — нет: та же модель и та же
конфигурация на RTX 3060 и RTX 5070 Ti дают одинаковую долю по целой части (100 %),
но разную долю полностью точных, причём порядок промптов между собой меняется на
противоположный. Это и есть мера того, чего стоит различие в одну фикстуру из пяти:
доля по целой части воспроизводится, доля точных — нет.

Видеопамяти сверх 10 ГБ задача не требует: победившая модель занимает 9.8 ГБ и
одинаково берёт порог на обеих картах. Разница только в скорости — 10 секунд на
снимок против 60.

Ориентир по VRAM:

| VRAM | Модель |
|---|---|
| 6–8 ГБ | qwen2.5vl:7b (Q4) |
| 12–16 ГБ | qwen2.5vl:7b (fp16) или gemma3:12b |
| 24 ГБ | qwen2.5vl:32b (Q4) |
| 48 ГБ+ | qwen2.5vl:72b |

Ollama требует NVIDIA с compute capability не ниже 5.0. Альтернативы для сравнения:
minicpm-v, llama3.2-vision:11b, internvl.

Каждая неверно распознанная фотография добавляется в фикстуры и становится
регрессионным тестом.

## Проверка распознанного

`ReadingValidator` из Core, уже готов и покрыт тестами. Проверяет: значение не меньше
предыдущего, потребление в разумных пределах от медианы, разрядность, совпадение
серийника, порог уверенности. Ничего не блокирует — размечает, на что смотреть.

Критические замечания (значение меньше предыдущего, несовпадение серийника, выход за
диапазон) должны удерживать отправку даже при `dryRun = false`.

## Хост обработчика

WPF-приложение с иконкой в трее, внутри — Generic Host с фоновыми службами.

Почему не служба Windows: нужен интерактивный сеанс для входа в кабинет в видимом
браузере при первой настройке и для локальной привязки Dropbox.

| Служба | Задача |
|---|---|
| `DropboxWatcherService` | longpoll по /queue/to-desktop и /photos; при ошибке — опрос |
| `PhotoBatchService` | готовность пачки, сопоставление файлов со счётчиками, запуск распознавания |
| `MessageProcessorService` | захват задачи, обработка, done/failed |
| `DeadlineWatchdogService` | ежечасно: срок и льготный период прошли, показаний нет — прогноз |
| `HealthPublisherService` | heartbeat в /queue/to-mobile |

Локальное состояние — SQLite (EF Core): readings, processed_messages, submissions,
recognition_runs. Логи — Serilog в `%LOCALAPPDATA%\WaterCounters\logs`.

У `submissions` есть отпечаток пачки фотографий — пути и ревизии файлов. Без него
пачка, которую не удалось обработать, крутилась бы в цикле, рассылая письма каждую
минуту; с ним повтор запускается только когда фотографии действительно изменились
либо прошлая попытка сорвалась по устранимой причине (не ответил VLM-хост, не
открылся кабинет). Нечитаемый снимок устранимой причиной не считается: повторять
нечего, нужен новый кадр.

## Порядок работ

1. ✅ `WaterCounters.Recognition`: контракт, StubRecognizer, OllamaRecognizer,
   OpenAiCompatibleRecognizer, EnsembleRecognizer, схема ответа.
2. ✅ Предобработка OpenCV и bench-харнесс `tools/WaterCounters.Recognition.Bench`.
3. ⏳ Подбор модели замерами. Порог 95 % по целой части взят: `qwen3-vl:8b-instruct-q8_0`
   с коротким промптом и отдельным проходом за серийным номером даёт 100 % по целой
   части, 80 % полностью точных, 2.6 % неверных цифр и 100 % серийных номеров. Пять фикстур для выводов мало — одна ошибка стоит 20 %, — поэтому конфигурация
   считается предварительной, пока не наберётся пара десятков снимков в разных условиях.
4. ✅ Хост: наблюдатель, определение готовности пачки, сопоставление со счётчиками.
5. ✅ Связка с `WaterCounters.Portal`, режим проверки, письмо.
6. ✅ Прогноз и watchdog срока.

Шаги 1 и 4–6 не потребовали GPU: за `IMeterRecognizer` подставляется StubRecognizer,
который берёт ожидаемое значение из разметки фикстуры.

## Критерии готовности

* Доля точных совпадений по целой части на фикстурах — не ниже 95%.
* Повторный запуск обработчика после падения не приводит к повторной отправке.
* При `dryRun = true` счётчик отправок на стороне кабинета остаётся нулевым.
* Критическое замечание валидатора удерживает отправку.
* Письмо приходит и при успехе, и при провале; при провале приложены скриншот и trace.
